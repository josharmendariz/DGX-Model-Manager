## Phase 2 head start — the math is already validated

A working prototype is preserved at
`.planning/phases/02-derived-launch-spec/kvcalc-prototype.py` — it reads every model config
on the box and prints both tables below. Run it first; it is scratch quality and exists to
be re-derived into `app.py` as a pure function, not to be imported.

**The load-bearing insight:** most models here are hybrid-attention, so a naive
`num_hidden_layers` KV estimate overestimates by 4–11x.

| model | attention layers / total | source field | KV fp8 @ max ctx | naive |
|---|---|---|---|---|
| Nemotron-3-Super-120B | 8 / 88 | `hybrid_override_pattern` | 1.1 GB @ 262k | 11.8 GB |
| Qwen3.6-35B-A3B-FP8 | 10 / 40 | `hybrid_override_pattern` | 2.7 GB @ 262k | 10.7 GB |
| qwen3-next-80b | 12 / 48 | `full_attention_interval` | 3.2 GB @ 262k | 12.9 GB |
| gpt-oss-120b | 18 full + 18 sliding(128) / 36 | `layer_types` | 2.4 GB @ 131k | 4.8 GB |
| R1-Distill-Qwen-32B (dense) | 64 / 64 | — | 17.2 GB @ 131k | 17.2 GB |

Precedence chain: `layer_types` → `hybrid_override_pattern` (count `*`) →
`full_attention_interval` → `num_hidden_layers`. VL models nest under `text_config`.

KV bytes/token = `2 × attn_layers × num_key_value_heads × head_dim × dtype_bytes`
(`head_dim` falls back to `hidden_size / num_attention_heads`).

Recommended util = `(weights + KV + ~6 GB overhead) / 121 + 0.04`.

**Calibration check to reproduce as a test:** this formula independently produced **0.54
for qwen3-next-80b against the hand-measured 0.55**. That agreement is the evidence the
approach is sound — if a refactor breaks it, the formula is wrong, not the recipe.

**Consequence worth keeping in view:** `--max-model-len 32768` is leaving nearly-free
context on the floor; utilization is the real memory lever, not context length. That is why
Phase 3 (curated recipes winning over derived values) matters — Qwen3.6's measured recipe
is 0.55 / 262144 / `qwen3_xml`, and the generator's generic defaults contradict it on all
three counts.

## Critical Anti-Patterns (do NOT repeat these)

- **Trusting a subagent's factual claims about the box** → every Codex finding in this audit
  was re-verified against live state before being acted on, and the process caught real
  nuance (e.g. the "flat-dir paths are unsafe for spaces" claim was wrong; those were
  correctly quoted). Verify before planning work around a finding.
- **Committing other sessions' dirty files** → `profiles/vLLM/start_hf_openai_gpt-oss-120b.sh`
  (modified) and `start_hf_qwen_qwen3-{8b,14b}.sh` (untracked) were dirty *before* this
  session and belong to someone else; there are ~6 concurrent claude processes in this repo.
  Commit by explicit path, never `git add -A`.
- **Verification that silently requires vLLM** → the whole phase was structured so every
  check is pytest, `bash -n`, a container mount inspection via
  `docker run --rm -v <mount> busybox`, or running the HF worker under `HF_HUB_OFFLINE=1`.
  Keep that discipline in Phase 2; it is a pure function and has no excuse to need a model.

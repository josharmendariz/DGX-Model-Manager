1. **Malformed script.** `start_hf_qwen_qwen3.6-35b-a3b-fp8.sh` predated the Phase 1

   `--restart` at all** — DMM is a manual switcher, the boot unit owns recovery.

   ~25 GB cached (refused to start, blaming `max_model_len`) vs 25.97 GiB after

## Hard-won lessons (do not re-learn these)

- **Parse the code, not the comments.** Load scripts quote the very commands preflight
  searches for; the Qwen3.6 profile reported its recipe as `(FP8,`, lifted out of its own
  `# Description:` line. `_script_code()` strips whole-line comments before any regex.
- **Expand shell variables** (`$HOME`, `RECIPE=…`) or docker rejects the mount as
  "invalid characters for a local volume name" — which reads as a corrupt model. Env
  expansion is allowlisted (`HOME`, `USER`) because the result is returned over HTTP.
- **Unresolvable is not broken.** `HASH=$(basename …)` cannot be resolved statically →
  report `skip`, never `fail`.
- **Only argparse's own vocabulary counts as "bad flags."** The probe runs GPU-less and
  vLLM builds pydantic config objects that touch the device, so everything else degrades
  to `skip`. A preflight that cries wolf gets ignored.
- **Progress must come from `docker logs -f`, not the `/tmp` launch log.** That log only
  captures the first foreground attempt: it is near-empty for `-d`/recipe launches and
  gone after a reboot. This is exactly why Josh's `/tmp` log "showed nothing".
- **Wait for a different container ID.** Attaching by name right after `POST /start`
  grabs the *outgoing* container; its removal reads as a crash. The first E2E run
  reported "failed" at 3.6s quoting a stray access-log line.
- **`Up` is not health.** On the recipe path vLLM runs as an exec inside a container that
  outlives its death — the container stayed `Up` for 12 minutes with a dead engine.
- **Never present arbitrary trailing output as "the error."** `_load_failure_reason` now
  says "No exception was logged. Last output: …" when it finds none.

## Known limitations (honest, not blocking)

1. **The memory check overstates while a model is loaded.** A running engine's ~70 GB is
   charged as unavailable with no reclaim credit, so `budget.usable_gib` goes negative and
   the verdict is `fail` even when a switch would succeed. The page-cache advice is still
   correct; the verdict is not. **This is Phase 5 work** — it needs the label-based reclaim
   identification (`dgx.profile=<id>`), which `_vram_admission_check` already approximates
   and preflight does not yet reuse.
2. **The argparse smoke test skips on generated profiles** (GPU-less probe can't build
   vLLM's device config). Static checks and the recipe dry-run both work fully. Fixing it
   means either passing `--gpus all` to the probe or finding a parse path that doesn't
   construct `DeviceConfig`.
3. **`_build_vllm_profile_script` still emits `-e VLLM_USE_FLASHINFER_MOE_FP4=0`** for
   gpt-oss and FP4 models, while the peer's uncommitted edit to
   `start_hf_openai_gpt-oss-120b.sh` says vLLM 0.23.1 no longer recognizes it and logs
   "Unknown vLLM environment variable". The generator and the hand-written profile now
   disagree. Worth reconciling in Phase 3.
